# dcheck — 문서 일관성 검토

## 언제 쓰나

- `/dcheck` 뒤에 확정 정책(결정 사항)을 붙여서 입력했을 때
- 회의·채팅에서 정한 정책이 기획 md에 다 들어갔는지, 문서끼리 다른 말을 하지 않는지 확인하고 싶을 때
- PR 리뷰 반영 뒤 빠진 곳이 없는지 다시 볼 때

검토 대상은 기본값이 safe-site-docs 저장소다. 사용자가 다른 저장소를 말하면 그 저장소다. 모노레포(법무 문서)는 사용자가 포함하라고 할 때만 본다.

## 입력

1. **확정 정책 목록**: 사용자가 붙여 넣은 글. 채팅 기록이 섞여 있으면 결정 문장만 D1, D2, …로 번호를 매겨 정리한다. 같은 주제에 서로 다른 결정이 두 개 있으면(예: 예전 채팅 "이미지 1년" vs 나중 PR 리뷰 "사진은 기록과 같이 보관") 둘 다 적고, 판정은 사용자에게 묻는다. 내가 고르지 않는다.
2. **저장소 위치**: origin/main 최신본을 새 워크트리로 받는다. 로컬 클론은 구버전일 수 있다.
   ```bash
   git -C ~/Documents/safe-site-docs fetch -q origin
   git -C ~/Documents/safe-site-docs worktree add -q <scratchpad>/ssd-main -b docs/<주제>-sync origin/main
   ```
3. **사이클 수**: 기본 5회. 사용자가 숫자를 말하면 그 수.

## 사이클

각 사이클은 **새 서브에이전트(general-purpose, 읽기 전용)** 하나가 검토하고, 내가 고친다. 같은 에이전트를 이어 쓰지 않는다(앞 판단에 끌려가는 것을 막기 위해).

### 1. 검토 에이전트 프롬프트에 꼭 넣을 것

- 파일 수정 금지, GitHub 쓰기 금지, 추측 금지, 인용 근거만, 한국어.
- 워크트리 경로와 읽을 범위: `plan/**/*.md` 전부, `deprecated/**/*.md`, 두 README. 큰 파일도 전체를 읽으라고 명시(sop-risk-alert.md, notification.md는 700~800줄).
- 정책 목록 D1~Dn 전문.
- 보고 항목:
  - A. 정책별로 (1) 정책을 적은 문서·줄 인용, (2) 어긋나는 문장 전부(file:line, 원문, 왜, 고칠 문장 제안), (3) 들어가야 하는데 없는 문서와 넣을 절·요구사항 행.
  - B. 문서 사이에 서로 다른 말을 하는 곳(한 쌍씩 인용).
  - C. 상대 링크 파일 존재 여부, yaml version과 변경 이력 최상단 일치, 표 칸 수, 괄호·백틱 짝.
  - 심각도(높음/중간/낮음). 변경 이력·"변경 전" 칸은 역사 기록으로 따로 분리.
- 사이클마다 같은 프롬프트로 전체를 다시 본다(사용자 지시 2026-10-14: 초점을 나누지 말고 같은 검토를 5회 반복). 앞 사이클 보고는 주지 않는다. 프롬프트는 파일로 저장해 두고 회차 번호만 바꾼다.
- 프롬프트에 "다른 에이전트에게 위임하지 말고 직접 읽어라", "grep 전수 검색을 직접 실행하고 확인 보류로 남기지 마라"를 넣는다. 위임하면 결과가 안 오거나 늦게 온다.

### 2. 보고 받은 뒤 내가 할 일

- 지적마다 파일을 직접 열어 사실인지 확인한다. 에이전트는 틀릴 때가 있다(없는 PR 번호를 "없다"고 하거나, 브랜치 중간 버전을 main 버전으로 착각). 확인 안 되면 반영하지 않고 사용자에게 알린다.
- 맞는 지적만 고친다. 고칠 때 규칙(기능명세 md는 `feature-generator` 스킬의 SKILL.md와 references/common_md_structure.md·feature_content_rules.md를 먼저 읽고 그 규칙을 따른다):
  - 메타 키는 `id·version·status·owner_team·effective_date`가 표준. `updated`를 새로 추가하지 않는다. 손댄 문서의 `owner_team`은 `AI Platform Team`으로 바꾼다.
  - 표 칸은 짧은 명사형, 설명 문단은 일상 동사. 예시는 문서에 있는 용어(PPE는 안전모·하네스·각반)로 든다.
  - 정책 문장은 한 문서에만 쓰고 다른 문서는 링크로 가리킨다(기능명세 md 분할 규칙).
  - 요구사항 행을 고치면 같은 행의 프로세스·화면·데이터 열도 같이 본다.
  - yaml `version`을 올리고 변경 이력 맨 위에 행을 추가한다(일자·내용·작성자 `Claude, hy0909`). 같은 날 결정이 여러 개면 날짜별로 행을 나눈다.
  - 사용자가 GitHub에서 직접 쓴 이슈 본문은 손대지 않는다. 고쳐야 하면 live 본문을 먼저 받고 필요한 줄만 바꾼다.
  - 디자인 값(px·hex·토큰)은 문서에 넣지 않는다. 피그마 기준이라고만 적는다.
  - 아직 정하지 않은 것은 `TBD`(담당 팀)로 적는다. `[확인 필요]`는 SOP 처리 상태 이름과 겹치니 쓰지 않는다.
  - 한국어는 human-writing 규칙(60자 안팎, 결론 먼저, 번역투·상투구 금지, `갈래`·`축` 금지).
- 고친 뒤 `grep`으로 옛 표현이 남았는지 한 번 더 찾는다.

### 3. 종료 조건

- 마지막 사이클 보고에 높음·중간이 0건이고, 낮음도 사용자 판단이 필요한 것(링크 공개 범위 같은 것)만 남아야 끝난다.
- 5회 안에 0건이 안 되면 멈추고 남은 것을 사용자에게 보고한다.
- 사이클이 끝나면 `git diff origin/main`만 읽는 에이전트를 한 번 더 띄운다. 바꾼 줄끼리 어긋나는 곳, 문장 길이, 참조 번호를 본다.
- 정책 범위 밖의 기존 불일치(처리 상태 명칭, 권한 키 이름 등)는 고치지 않고 목록으로 모아 보고한다.

## 끝내기

1. 커밋(한국어, AI 서명 없음)·푸시. 브랜치 이름 `docs/<주제>-sync`. `git add -A` 전에 `git status`로 지워진 파일이 없는지 본다(워크트리가 깨지면 파일이 통째로 빠질 수 있다).
2. 이슈·PR은 만들지 않는다. 사용자가 "이슈 올려" "PR 올려"라고 하면 그때 issue-generator·pr-generator 규칙대로.
3. 보고 형식:
   - 첫 줄에 결과(사이클 n회, 마지막 사이클 0건인지).
   - 표: 정책 | 고친 문서·위치 | 바꾼 점 | 출처(사용자·리뷰어 결정 / 문서 내 정리 / 내 판단). 내 판단으로 바꾼 것은 따로 묶어 되돌릴 수 있게 한다.
   - 사용자가 정해야 할 것(서로 다른 결정이 있던 항목, 링크 공개 범위 등).
   - 손대지 않은 것과 이유.
