# 올리기 전 검토 (이슈·이슈 댓글·PR)

기획·기능명세 MD를 다룬 작업을 GitHub에 올리기 직전에 쓰는 검토다. 이슈를 만들 때, 이슈에 댓글을 달 때, PR을 만들 때 세 경우 모두 해당한다 (사용자 규칙 2026-10-26).

## 1. 항상 먼저 묻는다

올리는 명령을 실행하기 전에 `추가 검토할까요?`라고 반드시 묻는다. 질문과 선택지는 `issue-generator`·`pr-generator`의 「올리기 전 추가 검토」와 같다 (사용자 규칙 2026-10-29).

- Claude Code에서는 AskUserQuestion 도구로 묻고, 여러 개를 고를 수 있게 한다.
- 선택지: `1. 일관성·충돌·개발 영향`(이 문서 2~4절의 서브에이전트 세 개), `2. 예외·에러 케이스`(`coverage_exception_review.md` 기준 서브에이전트 하나), `3. 선택 안 함`.
- 사용자가 답하기 전에는 `gh issue create`, `gh issue comment`, `gh pr create`를 실행하지 않는다.
- 같은 작업에서 내용이 바뀌어 다시 올릴 때도 다시 묻는다. 한 번 받은 답을 다음 게시물에 그대로 쓰지 않는다.

## 2. 검토 범위를 정한다

서브에이전트를 띄우기 전에 아래를 직접 확인해서 각 서브에이전트에게 넘긴다.

| 항목 | 확인 방법 |
| --- | --- |
| 저장소·기준 브랜치 | `git remote -v`, 보통 `main` |
| 작업 브랜치 | `git branch --show-current` |
| 바뀐 파일 | `git fetch origin main` 후 `git diff --name-status origin/main...HEAD` |
| 올릴 글 | 이슈·댓글·PR 본문 초안 전체 |
| 비교할 문서 폴더 | 기획·기능명세 MD가 모인 폴더 (예: `plan/feature/`, `docs/feature/`) |
| 관련 이슈·PR | 본문에 적힌 번호, `gh pr list --state open` |

브랜치가 없는 이슈·댓글이면 바뀐 파일 대신 "글이 언급하는 문서"를 범위로 잡고, 비교 기준은 `origin/main`으로 한다.

## 3. 서브에이전트 세 개를 동시에 띄운다

Claude Code에서는 Agent 도구로 세 개를 한 번에 띄운다. 서브에이전트를 쓸 수 없는 환경(Codex 등)에서는 같은 세 가지 검토를 차례로 직접 한다.

공통 지시:

- 읽기만 한다. 파일 수정, 커밋, 푸시, 이슈·PR 작성은 하지 않는다.
- 발췌가 아니라 관련 문서 전체를 읽는다. 문서가 많으면 읽은 목록과 건너뛴 목록을 나눠 보고한다.
- 모든 지적에는 근거 위치를 `파일:줄` 또는 `파일 요구사항 ID`로 붙인다. 근거가 없는 추측은 `확인 필요`로 따로 적는다.
- 결과는 아래 4절 표 형식으로만 돌려준다.

### 3-1. 기획·기능명세 일관성

이번에 바뀐 MD와 올릴 글을 main에 있는 다른 기획·기능명세 문서와 맞춰 본다.

- 같은 대상을 부르는 용어, 상태 이름, 역할 이름, 버튼 이름이 문서마다 같은지
- 같은 규칙의 숫자·시간 기준·조건이 문서마다 다르게 적혀 있지 않은지
- 요구사항 ID가 다른 문서와 겹치거나 번호 규칙에서 벗어나지 않았는지
- 같은 내용을 두 문서에 적어 둔 곳 (`No Duplication Across MDs` 규칙 위반)
- 개요 MD의 `기획 결정 현황`과 페이지 MD 내용이 어긋나지 않는지
- 이번 변경 때문에 다른 문서의 설명이 틀린 말이 되는 곳

### 3-2. main 병합 시 개발 쪽 문제

이대로 main에 들어갔을 때 FE·BE 개발자가 막히거나 잘못 만들 수 있는 곳을 찾는다.

- 개발자가 두 가지로 읽을 수 있는 요구사항, 결과가 적히지 않은 조건
- 빠진 상태: 빈 화면, 불러오는 중, 오류, 권한 없음, 부분 성공
- 구현을 막는 `TBD`와 그 담당 팀이 적혀 있는지
- 지워지거나 뜻이 바뀐 요구사항 중 이미 구현됐거나 다른 이슈가 기대고 있는 것 (`gh issue list`, `gh pr list`로 요구사항 ID·파일 이름 검색)
- 저장소에 FE·BE 문서나 코드가 있으면 그 내용과 어긋나는 데이터 뜻, 권한, 처리 순서
- 문서 안 링크가 main 기준으로 열리는지, 병합 후에도 없는 파일을 가리키지 않는지

### 3-3. 충돌 사항

git과 GitHub 기준으로 병합을 막거나 덮어쓸 수 있는 곳을 찾는다.

- `git merge-tree --write-tree origin/main HEAD`로 충돌 파일 확인
- 브랜치를 딴 뒤 main에서 같은 파일이 바뀌었는지: `git log HEAD..origin/main -- <파일>`
- 열린 다른 PR이 같은 파일을 고치는지: `gh pr list --state open --json number,title,files`
- 같은 요구사항 ID나 같은 화면을 다루는 열린 이슈·PR이 있는지
- 변경 이력 표가 main 쪽 이력을 지우거나 순서를 바꾸지 않는지

## 4. 결과를 모아 보고한다

서브에이전트 결과를 그대로 옮기지 않는다. 각 지적의 근거 위치를 직접 열어 맞는지 확인한 뒤, 확인된 것만 표에 남긴다. 확인하지 못한 것은 `확인 필요`로 적는다.

| 심각도 | 검토 | 위치 | 문제 | 근거 | 권장 조치 |
| --- | --- | --- | --- | --- | --- |

심각도는 세 가지만 쓴다.

- `병합 막음`: 그대로 올리면 충돌이 나거나 개발이 잘못된 방향으로 간다
- `병합 전 권장`: 올릴 수는 있지만 고치고 올리는 편이 낫다
- `참고`: 이번 작업 범위 밖이지만 알아 둘 것

지적이 없으면 `중요 문제 없음`과 함께 무엇을 어디까지 봤는지 한 줄로 적는다. 볼 수 없었던 문서·권한이 있으면 통과라고 말하지 않고 빠진 것을 적는다.

## 5. 고칠 것을 묻고 나서 올린다

- 보고 뒤 어떤 지적을 반영할지 묻는다. 반영은 현재 작업 MD에만 하고, 다른 문서는 사용자가 따로 허락할 때만 고친다.
- 반영 후 바뀐 부분에 영향을 받는 검토만 다시 돌린다.
- `병합 막음`이 남아 있으면 올리지 않고 사용자에게 다시 확인한다.
- PR 본문에는 검토 결과를 한 단락으로 남긴다: 무엇을 비교했는지, 남은 `병합 전 권장`·`참고` 항목. 이슈·댓글에는 사용자가 원할 때만 넣는다.
